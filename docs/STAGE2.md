# 第二阶段实现与测量记录

2026-10-25：本阶段已在用户的 openEuler 24.03 LTS-SP3 x86_64 虚拟机中完成验证。

## 本阶段交付

1. 新增两个读者竞争同一管道的测试，验证重试与唤醒；新增周期 SIGALRM 中断 poll 的测试，验证原有截止时间不会因反复中断而丢失。
2. 实现相同固定计算量的阻塞用户线程、事件驱动用户线程和 pthread 三种对照。
3. 完成每种方式 1 轮预热、20 轮有效测量，保留 60 份有效测量记录及相应原始轨迹；每轮随机排列三种方式的执行顺序。
4. 生成可离线打开的 HTML 报告，包含统计对比、真实状态区间、程序标记、回放、缩放和 CSV 导出。

## 实际环境和方法

- VirtualBox：2 个虚拟 CPU，4096 MB 内存。
- openEuler：24.03 LTS-SP3，内核 6.6.0-132.0.0.111.oe2403sp3.x86_64。
- GCC 12.3.1，glibc 2.38，Python 3.11.6。
- 三种方式的子进程均绑定到虚拟 CPU 0；不代表独占主机物理 CPU。
- 工作任务执行 40 步，每步 100000 次固定 xorshift 计算，所有方式的最终计算校验值一致。
- 独立写入进程等待 100 ms 后写入管道。先 fork，再创建 pthread，避免在多线程状态下 fork。
- 总完成时间包含初始化、fork 和等待写入进程退出；轨迹文件写出位于计时区间之外。
- CPU 时间统计主进程及其线程，不包括独立写入进程。共同的程序标记记录器有锁保护，用户线程还保留内部状态记录，不能把结果称作无观测开销的极限性能。

## 本次测量结果

各列除“轮数”外均为 20 次有效测量的中位数。

| 执行方式 | 轮数 | 工作任务首次推进 ms | 总完成时间 ms | 读完成前工作推进次数 |
| --- | --- | --- | --- | --- |
| 阻塞用户线程 | 20 | 107.455 | 114.800 | 0 |
| 事件驱动用户线程 | 20 | 0.205 | 116.620 | 40 |
| pthread | 20 | 0.238 | 135.180 | 40 |

首次推进时间的四分位区间依次为 102.548–123.341 ms、0.164–0.217 ms、0.216–0.265 ms。

可以支持的结论：在本次受控工作负载中，事件驱动等待避免了读者等待期间其他任务完全停滞，首次推进时间与 pthread 处于同一毫秒以下数量级。

不能据此支持的结论：事件驱动在所有任务中都更快，或本实现整体优于 pthread。本次事件驱动总完成时间中位数略高于阻塞方式，且各方式离散程度较大；应继续研究不同负载与虚拟化噪声。CPU 记账和峰值 RSS 还受内核、启动方式与观测影响，不用这些列推断运行时本体的资源优势。

## 复现

```sh
cd /home/oslab/oslab-project/uthread-lab
sh scripts/validate_stage2.sh
```

运行会创建新的带时间标记的 benchmark 目录。报告默认使用最新一份通过校验的重复实验；也可用 `python3 scripts/make_report.py --benchmark 路径/benchmark.json` 指定已有数据。

只在验证通过后解读统计结果；失败或不完整的测量不会被报告生成器当作成功数据展示。
