# 第二轮：就绪选择与 I/O 等待表

本轮对照固定为第一轮完成版本 `1afe8e479650a47ca1faff5e4579dc1930a598e4`，其运行时完整保存在 `benchmarks/round1/uthread.c`。下面的增量比较不与第一轮相对原版的百分比相加。

## 实现

- 用 32 位就绪位图选择任务。轮转从上次任务之后取最低就绪位，到末尾后回绕；first-ready 始终选择最低位。第 31 位的移位边界单独处理，避免移位 32 位的未定义行为。
- I/O 等待表持续保存，每个 fd 只有一项 pollfd，用任务位图关联其等待者。任务进入等待时登记，就绪或超时后移除，不再每轮重新扫描任务数组构造 pollfd。
- 缓存最近截止时间，只在等待成员变化时重算。poll 未返回事件且没有到期者时直接返回；仍在每个调度边界检查 I/O。
- 同一 fd 的读者保留各自截止时间。某个读者超时不会删除其他读者；就绪唤醒后重新 read，竞争失败仍按原截止时间等待。

这仍是最多 32 个任务、单内核线程的协作调度器。poll 内核检查仍随不同 fd 数量增长，位图和去重不等于 epoll，也不提供多核并行。

## 回归与复现

```sh
make check
make wait-perf-check
```

新增回归覆盖同 fd 不同超时、同时就绪时等待表删除与压缩、等待中关闭 fd 的 POLLNVAL、第 32 个任务的轮转回绕和已完成槽位复用。测试检查实际系统调用参数，再调用内核 poll；同时覆盖普通 poll 和 Ubuntu 强化后的 __poll_chk，不关闭 libc 检查。已有竞争读者、EOF、信号中断、日志与 errno 测试继续运行。

两版使用相同编译选项、完整记录、同一个允许的 CPU。每个组合预热一次，再随机安排两版执行顺序，各保留 20 次有效测量：

- 纯调度：1、8、32 个任务，每个执行 1000 次 yield。
- 等待：1、8、31 个读者，共享一个管道或各用一个管道，生产者先 yield 1000 次，再为每个读者写一个字节。

等待基准用固定工作量检查表维护开销，不模拟真实请求延迟或吞吐量。计时包括初始化、任务创建和执行，不包括管道创建、轨迹导出和销毁。脚本校验任务完成数、计算校验值和完整记录；保存全部样本、CPU 时间、poll 次数、源码哈希及环境。每个环境共 360 条正式测量。

## 结论边界

CI 的 openEuler 容器共享宿主 Linux 内核，不能当成本机 openEuler 虚拟机测量。纯调度已受到上下文切换和日志成本限制，位图不保证带来明显收益；共享 fd 的等待基准更能反映去重效果。不同 fd 较多时仍需内核逐项检查。

## 已验证结果

2026-10-26，[CI 40336853277](https://github.com/codingsjx/openeuler-uthread-lab/actions/runs/40336853277) 在 openEuler 24.03 LTS-SP3 容器与 Ubuntu 上均通过严格编译（-O2 -g -std=c11 -Wall -Wextra -Wpedantic -Werror）、全部 C 回归及 4 项 Python 检查，并完成新旧两种基线对照。下表取第二轮相对第一轮的完整记录测量，每格为 20 次有效运行的耗时中位数。

| openEuler 容器工作负载 | 第一轮 μs | 第二轮 μs | 中位数下降 |
| --- | --- | --- | --- |
| 纯调度，1 任务 | 125.0 | 123.0 | 1.60% |
| 纯调度，8 任务 | 5297.0 | 5272.5 | 0.46% |
| 纯调度，32 任务 | 21293.5 | 21218.5 | 0.35% |
| 共享管道，1 读者 | 977.5 | 968.0 | 0.97% |
| 共享管道，8 读者 | 1388.5 | 1126.5 | 18.87% |
| 共享管道，31 读者 | 2589.5 | 1448.5 | 44.06% |
| 独立管道，1 读者 | 998.5 | 987.5 | 1.10% |
| 独立管道，8 读者 | 1387.5 | 1330.5 | 4.11% |
| 独立管道，31 读者 | 2670.0 | 2458.0 | 7.94% |

纯调度差异较小，不能据此宣称位图显著加速上下文切换。主要改善集中在多个任务共享 fd 时，减少了每轮重建和重复提交等待项。31 读者共享场景中，第二轮的 Q1/Q3 为 1430.5/1470.0 μs；两版的 poll 次数均为 1032、任务切入次数均为 1063（全部样本一致），没有减少调度边界的 I/O 检查。

Ubuntu 中，31 读者共享场景由 3241.0 降至 2158.5 μs，下降 33.40%；独立管道由 3290.0 降至 3114.0 μs，下降 5.35%。Ubuntu 的 8 任务纯调度由 8491.0 变为 8493.0 μs，单读者共享场景由 1617.5 变为 1621.0 μs，略有增加，说明收益依赖工作负载，微小差异不能排除噪声。

这批结果说明固定合成负载下的开销变化，没有测量真实网络吞吐、请求延迟分布或长期运行稳定性。第一轮与第二轮的机器、负载不同，不能把不同批次百分比直接叠加。
